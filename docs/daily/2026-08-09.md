## Problemas encontrados y su causa raíz

### 1. Bug de desplazamiento al origen (F1_CONTEXTO_POT_v04.py)

**Síntoma:** El lote y polígonos de vecinos no se desplazaban correctamente a (0,0,0). El vértice de anclaje era un punto fantasma.

**Causa raíz:** El script calculaba el offset como:
```python
offset_x = min(lote_xs)    # mínimo X entre TODOS los vértices
offset_y = min(lote_ys)    # mínimo Y entre TODOS los vértices
```
Estos dos mínimos pueden provenir de **vértices diferentes**. Resultado: el punto `(min_x, min_y)` no existe en el predio — es un punto fantasma.

**Corrección:** Buscar el vértice real del lote más cercano a la esquina SW del BoundingBox:
```python
bbox_min_x = min(v[0] for v in lote_verts)
bbox_min_y = min(v[1] for v in lote_verts)
# Buscar vértice REAL más cercano a (bbox_min_x, bbox_min_y)
for v in lote_verts:
    d = (v[0] - bbox_min_x)**2 + (v[1] - bbox_min_y)**2
    if d < min_dist:
        offset_x = v[0]  # ← vértice real
        offset_y = v[1]
```

### 2. Clasificación de lados incorrecta (fetch-urban-context-v5.py)

**Síntoma:** El JSON siempre tenía `"vias": []` vacío. Sin datos de vías, todos los bordes del lote se clasificaban como "Lateral" y no se generaban patios.

**Intentos fallidos:**
- ❌ **Buffer difference:** `buffer(75m) − union(todos los lotes)` → vacío porque en zona urbana densa los vecinos cubren todo el buffer.
- ❌ **Offset artificial:** Generar líneas a 15m hacia afuera desde cada borde. No funciona para lotes con un solo frente, lotes de esquina, o frentes opuestos. Es una inferencia sintética, no basada en datos reales.

**Aprendizaje clave:** La clasificación de lados NO debe basarse en líneas artificiales. Debe basarse en la **adyacencia real con vecinos** desde los datos GIS.

**Corrección final:** Para cada borde del lote:
1. Crear zona de búsqueda (buffer estrecho hacia afuera del segmento)
2. Verificar si algún vecino intersecta esa zona
3. **SÍ hay vecino → "Lateral"** (colinda con predio vecino)
4. **NO hay vecino → "Frontal"** (da a vía o espacio público)

Resultado en el JSON:
```json
"lados": [
  {"lado_idx": 0, "clasificacion": "Frontal", "vecino_colindante": null},
  {"lado_idx": 1, "clasificacion": "Lateral", "vecino_colindante": "AAA0128XYZA"}
]
```

### 3. Simplificación de la pipeline de patios

**Antes:** `LADOS_CONFIGURAR_v07 → PATIO_VECINO_v04 → PATIO_ESQUINA_v03 → PATIO_DIRECTO_v05`

**Después:** `Discontinuity → F1_PATIO_DISCONTINUIDAD_v02`

El componente nativo `Discontinuity` de Grasshopper encuentra directamente las esquinas del polígono, eliminando la necesidad de detectar colinealidad manualmente.

## Aciertos

1. **Diagnóstico correcto del bug de desplazamiento:** Identificar que `min(x)` y `min(y)` provenían de vértices distintos fue clave. El fix es simple y robusto.
2. **Pivotar de v07 simplificado a v06 como base:** La decisión de abandonar el formato simplificado (lossy) y trabajar desde v06 (conexiones intactas) evitó semanas de reconstrucción manual.
3. **Reconocer que el offset artificial no sirve:** Escuchar el feedback del usuario ("eso es una mala inferencia") y cambiar a clasificación por adyacencia real fue el giro correcto.
4. **Usar Discontinuity en vez de detección manual de colinealidad:** Simplifica radicalmente el canvas y elimina una clase entera de bugs.

## Errores y lecciones

1. **Asumir que `buffer.difference()` funciona en cualquier contexto urbano:** En zonas densas, el buffer de 75m es insuficiente para encontrar espacio público entre lotes. No se puede asumir que siempre hay gaps.
2. **Proponer offset sintético sin considerar casos de borde:** Lotes interiores (1 frente), lotes de esquina (2 frentes), lotes pasantes (frentes opuestos). Cada configuración requiere datos reales, no líneas inventadas.
3. **No verificar que el JSON existente tuviera `vias` antes de depender de ese campo:** Perdí tiempo debuggeando en Grasshopper cuando el problema estaba en el backend.
